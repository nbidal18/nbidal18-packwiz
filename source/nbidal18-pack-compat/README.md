# nbidal18 Pack Compatibility Enforcer

This first-party Fabric companion enforces the nbidal18 login identity and a secondary runtime integrity deterrent. It depends on the official Better Compatibility Checker 21.1.8 JAR and reads that mod's already-loaded `bcc-common.toml` identity through its public `getBetterStatus()` method. It does not contain, shade, or modify Better Compatibility Checker classes or assets.

On the client, it also adds a **Skins & Capes** button beside Mod Menu's full-width title-screen button. The button opens Skin Overrides' existing public selector screen; this companion does not copy or replace Skin Overrides logic, classes, or assets. A collision-checked top-right fallback is used when another title-screen layout does not expose the expected full-width Mods button.

Protocol 2 added the client's strict-manifest SHA-256 and clean/dirty status to the existing login response. Protocol 3 retains those fields and adds a bounded, sanitized local integrity reason so a rejected player sees the actual failing check. The server requires the digest to match `config/nbidal18-pack-compat.properties`:

```properties
expected-manifest-sha256=<64 lowercase hexadecimal characters>
```

The generated config is deliberately external to the JAR, so each release can update the expected digest without rebuilding this mod. A protocol-3 dedicated server rejects missing/malformed policy config, older clients, dirty clients, and digest mismatches. It validates pack identity and the manifest digest before displaying any client-supplied diagnostic reason, then sanitizes that reason again. The login-query initializer is deliberately disabled in Fabric's client environment, so an integrated singleplayer server does not apply the dedicated-server gate. A 1.1.6 client still emits the exact historical response requested by a protocol-1 or protocol-2 server, including no trailing reason field for protocol 2; a 1.1.6 dedicated server requires protocol 3.

On the client, initialization requires a valid `.nbidal18/strict-manifest.tsv`, a matching successful `.nbidal18/integrity-attestation.tsv` no more than 15 minutes old, an independent exact set/type/hash pass over every loadable managed root, and the narrow resource-pack, Iris, and Controlify security settings. This deliberate second process-local hash pass closes the guard-to-game-JVM replacement window. A declared regenerate-prefix that an earlier client initializer has already created remains explicitly uncaptured and pending during this pass; it is captured and locked only after initial resource loading completes. General config files are attested only at pre-launch because trusted mods rewrite them during startup.

The client also hash-captures Fabric's `.fabric/processedMods` and `.fabric/remappedJars` generated-code caches and CustomSkinLoader's `CustomSkinLoader/Core` executable cache, then keeps their exact file, directory, type, size, metadata, and content baselines immutable. The official `customskinloader-bootstrap` mod overwrites/extracts its deterministic core before Fabric client entrypoints run. When that mod is loaded, the core baseline is required to exist and contain files; a missing or empty core fails closed. The root may be absent only when the bootstrap mod is absent, and even that absent baseline is watched so later creation is rejected. The manifest treats `CustomSkinLoader` as a strict runtime-monitored directory: the declared `Core`, `LocalSkin`, `caches`, and `ProfileCache` runtime prefixes retain their specific mutable semantics, while undeclared plugin, extra-list, or other loadable content is rejected. Release-managed inert marker files keep `CustomSkinLoader/Plugins` and `CustomSkinLoader/ExtraList` present before initialization; only those exact hashed files are allowed there. Windows may also report a legitimate child write as an `ENTRY_MODIFY` on the parent strict-root directory; only that metadata event on an intact plain strict root is ignored, with an immediate metadata rescan requested, while root create/delete/replacement and every unexpected child event stay fail-closed. `moonlight-global-datapacks`, `villagerpacks`, and `server-resource-packs` must remain existing, completely empty directories. The launch guard purges Moonlight's `dynamic-resource-pack-cache` and every declared regenerate-prefix before it writes the fresh attestation. `CLIENT_STARTED` only arms pending verification because Fabric emits it while the splash screen is still visible; an end-of-tick check finalizes only after Minecraft's monotonic `isGameLoadFinished()` readiness signal becomes true. It then requires a plain, nonempty Moonlight tree with `hash.txt`, captures the entire tree, and locks every captured directory/file/metadata/hash for that process.

Any watcher event in an ordinary loadable strict root is a sticky immediate failure; only explicitly declared settings/runtime paths and generated-root writes before the post-resource-load finalization boundary are exempt. Periodic workers remain dormant until the synchronous startup boundary audit has locked generated trees, rechecked generated executable caches, closed-empty roots, and security settings; their intervals are then armed from that completed boundary. A metadata scan fills watcher gaps every 15 seconds, and a full hash scan runs every five minutes. Security seed templates are re-hashed during each targeted settings scan. The declared Euphoria shader tree is optional: if it exists when initial resource loading finishes, synchronous finalization requires a plain, nonempty tree and makes that launch's exact captured tree immutable. If it is absent at that boundary, creating it later is a sticky failure and requires a clean relaunch. Every create, modify, or delete event in either generated root after finalization fails immediately; deleting or restoring transient content cannot return the process to clean. Failures disconnect the local client with a repair instruction; nothing is deleted or quarantined in game. Non-clean protocol-2 responses retain their historical wire format and log the exact local reason; protocol 3 additionally sends the sanitized reason to the server for the rejection screen.

Per-launch generated-tree baselines deliberately replace release-wide generated-byte pins because Moonlight and Euphoria can produce legitimate machine-dependent bytes. This trusts only output present after a fresh guard purge/attestation and initial resource load, while exact manifest-hashed producer mods and managed configuration remain the root of trust. It slightly widens the trusted startup window before the baseline lock; after lock, watcher events are sticky and periodic exact scans remain fail-closed. Baselines are never persisted or reused across launches.

This is defense in depth, not remote attestation. A user who modifies the companion itself can forge client-reported state. Server protocol enforcement, exact expected digests, the separate pre-launch guard, and runtime monitoring raise the effort required but do not turn a user-controlled client into a trusted machine.

## Reproducible build

The checked-in Gradle wrapper pins Gradle 9.2.1. Fabric Loom, Minecraft, Fabric Loader, Fabric API, Better Compatibility Checker, and JUnit versions are pinned. Archive timestamps are disabled and entry order is deterministic.

```powershell
.\gradlew.bat clean test remapJar --no-daemon
Get-FileHash .\build\libs\nbidal18-pack-compat-1.1.6+1.21.1.jar -Algorithm SHA256
```

The Better Compatibility Checker and Skin Overrides dependencies are resolved from Modrinth's Maven endpoint for compilation only; neither is bundled in the output.
