## Strict file policy

The generated `.nbidal18/strict-manifest.tsv` defines a closed set beneath `mods/`, `resourcepacks/`, `shaderpacks/`, `datapacks/`, `config/`, `defaultconfigs/`, `CustomSkinLoader/`, `moonlight-global-datapacks/`, `villagerpacks/`, and `server-resource-packs/`. The final three roots are intentionally empty because their loaders can otherwise inject nonstandard datapacks or resource packs. `CustomSkinLoader/Plugins` and `CustomSkinLoader/ExtraList` are deliberately not exceptions, so injected plugin/provider files are quarantined. Pack-owned entries must match their exact SHA-256. The manifest also names every permitted seed-once setting, runtime file/cache, regenerated prefix, shader sidecar, and optional private exception; anything else in those roots is unapproved.

Every click of **Play** performs three checks before Minecraft starts:

1. A normal Packwiz pass applies the release update using the prior state, including removal of files retired from the manifest.
2. The guard removes that state and forces a second Packwiz pass, causing Packwiz to hash the full current pack and repair missing or modified managed files.
3. The independent launch guard SHA-256-verifies all strict entries, enforces the closed set and protected settings, purges Fabric's generated nested/remapped-mod caches and Moonlight's loadable dynamic resource-pack cache, then writes the integrity attestation consumed by the in-game companion.

Only missing, changed, or newly released payloads are downloaded, but an unchanged launch is deliberately not a no-op: it still performs full Packwiz and guard verification. An unexpected file or wrong optional file is moved, with its relative path preserved, to `minecraft/.nbidal18/quarantine/<run>/`. Quarantine is recoverable and must not be treated as an approved location from which Minecraft can load content.

The six-file launcher ZIP contains exactly:

- `.packignore`, `instance.cfg`, `mmc-pack.json`, and `server-icon.png`;
- `minecraft/nbidal18-launch-guard.jar`;
- `minecraft/packwiz-installer-bootstrap.jar`.

It contains no Packwiz-managed payload, settings, VinURL data, Still Life, shaders, or other player data. During the historical 3.1.0 -> 3.1.1 guard transition, the older five-file direct-bootstrap instance could not acquire the guard or replace its Prism pre-launch command through Packwiz, so that cutover required one new import. Existing guarded instances update to 3.2.3 in place unless the launcher shell changes again. Packwiz updates Minecraft content but does not rename an already imported Prism instance; new imports use the stable `nbidal18-client` identity.

## Personal and runtime state

The guard seeds declared ready-to-use settings only when their player-owned target is absent. Keybinds and the other declared settings then survive updates. Three security-sensitive mixed settings remain enforced on every launch:

- the `resourcePacks` and `incompatibleResourcePacks` lines in `options.txt` are restored to the canonical release;
- Iris permits only `ComplementaryUnbound_r5.8.1.zip`, `MakeUp-UltraFast-9.4b.zip`, or no shader, and `allowUnknownShaders=false` is forced;
- Controlify's `global.reach_around` is forced to `OFF`.

The two supplied shader ZIPs are exact managed entries. Only the two matching `.zip.txt` sidecar paths are personal, and their contents are preserved; arbitrary shader packs, resource packs, mods, and datapacks are not permitted. The Euphoria generated Complementary directory is explicitly discarded at launch and regenerated by the exact pack mods.

These are preserved outside the strict content policy: saves, screenshots, logs, crashes, recordings, generated VinURL data/helpers, personal skin/cape images under `skin_overrides/` and `cape_overrides/`, and narrowly declared non-loadable runtime state. VinURL can perform a roughly 175 MiB first-ever bootstrap, but its managed default disables repeat startup update checks. CustomSkinLoader's config, local cosmetic textures, profile cache, and network cache are narrow runtime exceptions; its generated `Core/CustomSkinLoader-Common.jar` is executable rather than personal and is independently hashed and watched. Narrow runtime records inside `config` allow known trusted files that mods legitimately rewrite. Pack-owned configs are exact at launch, but general config is not continuously monitored during play because legitimate mods rewrite it. Generated loadable caches are not personal state: the guard purges the applicable caches and the companion locks their regenerated contents during play.

The Patreon-only `datapacks/Still_Life-1.0-beta1.zip` is never published or bundled. Its optional exception accepts absence or the exact approved private file with SHA-256 `6D6CF7C67D0FAA16B37C8A00A7FD39131AD1A9C43E4A3356B88E2EA9C39159BC`, and only for a user authorized by its creator. A wrong copy is quarantined.

## In-game integrity and limits

The client companion checks the launch attestation and monitors `mods`, `resourcepacks`, `shaderpacks`, `datapacks`, `defaultconfigs`, `CustomSkinLoader`, the three intentionally empty auxiliary pack roots, regenerated Fabric/Moonlight loadable caches, CustomSkinLoader's generated executable core, and the protected options/Iris/Controlify fields. The guard first purges the Euphoria and Moonlight generated roots. After exact managed producers finish initial resource loading, each launch captures its own immutable baseline: Moonlight's dynamic cache must be a plain, nonempty tree containing `hash.txt`; an existing Euphoria tree must be plain and nonempty, while absence is locked absent. This accepts legitimate cross-PC output differences without trusting a prior launch. Every post-lock watcher event remains sticky dirty, and metadata/full scans compare the captured directory/file types, metadata, and hashes. General config is not continuously watched for the runtime-write reason above.

Protocol 3 sends identity, the attested manifest digest, clean state, and a bounded sanitized local pending/failure reason. The server validates identity and manifest format/match before displaying that untrusted diagnostic reason, and still rejects every non-clean client. The new client answers protocol 1 and protocol 2 in their exact historical response shapes, so it can join an older server during rollout; the new server requires protocol 3 and rejects an old client as outdated. The gate becomes active only after the matching `4. server/2. online-hosting` payload is uploaded and the server is fully restarted. Per-launch capture trusts output produced inside the guard-clean pre-lock startup window, so the client-side security limitation below still applies.

All client-side integrity checks can ultimately be patched or spoofed by a player who controls the client. This system prevents accidental drift and raises the effort of casual tampering, but it cannot prove a client is honest. Use server-side anti-cheat and authoritative server validation for important multiplayer rules.

## One-time GitHub setup

This folder is connected to the public <https://github.com/nbidal18/nbidal18-packwiz> repository, and GitHub Pages publishes only `site/`. The steps below document how that one-time setup is maintained or recreated; never use the release root as the public repository working tree.

1. Run `SET-UPDATE-URL.bat` with `https://OWNER.github.io/REPOSITORY/pack.toml` using the real names.
2. Initialize this folder on branch `main`, connect the remote, commit, and push.
3. In the repository's Pages settings, select **GitHub Actions** as the publishing source.
4. Wait for the included `Deploy Packwiz update site` workflow to finish.
5. Open the final `pack.toml` URL in a private browser window to confirm anonymous access.
6. Before the first strict cutover only, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Build-Release.ps1 -SkipRemoteCheck`; import or distribute the resulting six-file ZIP, but do not launch the old direct-bootstrap instance after the next step.
7. Commit and push the strict site, then wait for the Pages workflow to finish.
8. Run `BUILD-FINAL-MIGRATION-ZIP.bat`. It refuses the final rebuild if the live `pack.toml`, `index.toml`, strict manifest, or reviewed internal-hosted payloads differ from `site/`.

## Routine release workflow

1. Edit the canonical client under `3. modpack/client` and appearance defaults under `2. appearance`.
2. Update the matching server payload and compatibility metadata when client/server compatibility changes. The server's expected manifest digest is generated from the same strict release.
3. Run `BUILD-UPDATE-SITE.bat`.
4. Review `metadata/METADATA-REPORT.csv`; do not approve a new raw file without its redistribution basis.
5. Run `TEST-UPDATE-SITE.bat`.
6. Commit and push this updater repository, then wait for GitHub Pages deployment.
7. Upload matching files from `4. server/2. online-hosting` to GameHostBros and fully restart the server so protocol 3 expects the new digest.

Players already using a guarded instance receive 3.2.3 in place on their next successful launch. The rebuilt six-file ZIP is for new or recovery installs; the one-time re-import requirement applied only to the historical 3.1.0 -> 3.1.1 guard transition. Players do not need Git or GitHub accounts.

## Failure behavior

Packwiz returns a nonzero error when a payload cannot be downloaded. Packwiz is not transaction-wide atomic, so some managed files can be written before a later payload fails. The launch guard treats either its normal or forced Packwiz pass failing as a blocked launch and does not issue a valid attestation. Retry after connectivity or hosting is restored; the next successful run must repair the managed client and pass the independent verification. Real Prism failure handling remains part of the final manual release check.
